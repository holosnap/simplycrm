# SES Setup — Foundation

This is the one-time AWS setup for email (see [EMAIL_SPEC.md](./EMAIL_SPEC.md) for the full design). It covers: domain identity + DKIM, a configuration set wired to SNS, account-level suppression/reputation, the IAM policy the *running app* uses, and how to confirm it all worked from inside the app. It does **not** cover sending/receiving code or SES production access — those come later.

## 1. Prerequisites

- An AWS account and a chosen region that supports SES sending (e.g. `us-east-1`).
- A domain/subdomain you control DNS for. Per EMAIL_SPEC.md §2, this should be a **dedicated sending subdomain** (e.g. `mail.simplycrm.app`), not your organization's apex domain.
- AWS credentials for whoever runs the provisioning script below, with enough permission to verify identities, create configuration sets, create an SNS topic, and change account-level SES settings. **This is intentionally more privileged than the app's own runtime credentials** (§4) — it's meant to be run once by a human operator via their own AWS CLI profile, not by the deployed app.

## 2. Run the provisioning script

```bash
cd server
cp .env.example .env   # fill in AWS_REGION, SES_SENDING_DOMAIN, SES_CONFIGURATION_SET, SES_FROM_ADDRESS
npm run ses:setup
```

The script (`server/scripts/ses-setup.ts`) is idempotent — safe to re-run any time, e.g. after changing `SES_CONFIGURATION_SET`. Each run:

1. Creates (or reuses) the `SES_SENDING_DOMAIN` identity with **Easy DKIM** — AWS generates and manages the signing key, we just publish the CNAME records it gives us.
2. Creates (or reuses) an SNS topic for SES events — named `<SES_CONFIGURATION_SET>-events` unless `SES_EVENTS_TOPIC_NAME` is set.
3. Creates (or reuses) the `SES_CONFIGURATION_SET` configuration set with **reputation metrics enabled**.
4. Wires a configuration-set event destination to that SNS topic, subscribed to exactly `Send`, `Delivery`, `Bounce`, `Complaint`, `Reject`, `DeliveryDelay` (not `Open`/`Click` — see EMAIL_SPEC.md §3 for why). If the destination already exists with different settings, it's **updated** to match, not left stale.
5. Enables the **account-level suppression list** for `BOUNCE` and `COMPLAINT`.
6. Best-effort enables account-level reputation tracking (Virtual Deliverability Manager's dashboard) — this is a newer SES surface; if your account/region doesn't support part of it, the script warns and continues rather than failing the whole run.
7. Rewrites §3 below with the real DKIM CNAME values it got back from AWS.

Run it, then open this file again — the table in §3 should no longer say "run `npm run ses:setup` to populate."

|---|---|---|---|
| DKIM CNAME 1 | *(run `npm run ses:setup` to populate)* | CNAME | — |
| DKIM CNAME 2 | *(run `npm run ses:setup` to populate)* | CNAME | — |
| DKIM CNAME 3 | *(run `npm run ses:setup` to populate)* | CNAME | — |
<!-- DKIM:END -->

Plus these two, which don't depend on anything AWS generates — add them yourself (substitute your actual sending domain):

| Record | Name | Type | Value |
|---|---|---|---|
| SPF | `SES_SENDING_DOMAIN` | TXT | `v=spf1 include:amazonses.com ~all` |
| DMARC | `_dmarc.SES_SENDING_DOMAIN` | TXT | `v=DMARC1; p=quarantine; rua=mailto:<your-dmarc-reports-address>; pct=100` |

Notes:
- `p=quarantine`, not `p=reject`, to start — per EMAIL_SPEC.md §2, tighten to `p=reject` once you trust your own sending hygiene and are seeing clean DMARC reports.
- DKIM verification (and therefore `DkimAttributes.Status` becoming `SUCCESS`) can take anywhere from a few minutes to up to 72 hours after the DNS records propagate. Don't be alarmed if §5's health check shows `PENDING` right after adding the records.
- Checklist, in order: add all 5 records above → wait for DNS propagation → confirm via §5 → (separately, later) request SES production access before sending to real, unverified recipients.

## 4. IAM policy for the running app

The app's own runtime credentials (not the ones used to run the script above) should be scoped to exactly this — nothing broader. The template is at [`server/aws/ses-iam-policy.json`](./server/aws/ses-iam-policy.json):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SendFromVerifiedIdentityOnly",
      "Effect": "Allow",
      "Action": ["ses:SendEmail", "ses:SendRawEmail"],
      "Resource": "arn:aws:ses:REGION:ACCOUNT_ID:identity/SES_SENDING_DOMAIN",
      "Condition": {
        "StringEquals": {
          "ses:FromAddress": "SES_FROM_ADDRESS",
          "ses:configuration-set": "SES_CONFIGURATION_SET"
        }
      }
    },
    {
      "Sid": "ReadIdentityForHealthCheck",
      "Effect": "Allow",
      "Action": "ses:GetEmailIdentity",
      "Resource": "arn:aws:ses:REGION:ACCOUNT_ID:identity/SES_SENDING_DOMAIN"
    },
    {
      "Sid": "ReadAccountStatusForHealthCheck",
      "Effect": "Allow",
      "Action": "ses:GetAccount",
      "Resource": "*"
    }
  ]
}
```

Before attaching: replace `REGION`, `ACCOUNT_ID`, `SES_SENDING_DOMAIN`, `SES_FROM_ADDRESS`, and `SES_CONFIGURATION_SET` with your real values (same ones from `server/.env`).

Why it's shaped this way:
- **`Resource` is the specific identity ARN**, never `"*"` — this credential can only ever send as `SES_SENDING_DOMAIN`, not any other identity that might exist on the same AWS account.
- **`ses:FromAddress` condition** pins the exact From address. If you later move to per-user sending addresses (EMAIL_SPEC.md §2's open question), this becomes a `StringLike` condition on the pattern instead of an exact `StringEquals` match — a deliberate follow-up, not an oversight.
- **`ses:configuration-set` condition** means a send call that omits — or names the wrong — configuration set is denied outright. There's no code path under this credential that can send mail outside the event pipeline in §2 without AWS itself refusing the call.
- **`ses:GetAccount` can't be scoped to a resource** — it's an account-wide read with no identity/resource dimension in SES's IAM model, so `Resource: "*"` is unavoidable for that one action specifically (verify this against the current [SES IAM action reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazonses.html) if it matters for your compliance posture — this doc wasn't fact-checked against live AWS docs at write time).
- **No `ses:List*`/`ses:Verify*`/`ses:Put*` here at all** — identity verification, configuration-set changes, and account settings are provisioning-time actions (§2's script), done with a human operator's own broader credentials, never with what the deployed app authenticates as.
- Credentials for this policy are attached to **an IAM role in deployment** and resolved via **env vars locally** (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` in `server/.env`, gitignored) — the app never reads, logs, or stores an access key anywhere, including the database. See `server/src/lib/ses.ts`.

## 5. Verify from the app

Log in as an admin → **Tags & Fields** settings page → **Email (AWS SES)** section → **Check connection**. This calls `GET /api/email/health`, which:

- Reports "not configured" if `AWS_REGION`/`SES_SENDING_DOMAIN` aren't set yet (no AWS call attempted).
- Otherwise calls `GetAccount` (confirms `SendingEnabled` and current suppression settings) and `GetEmailIdentity` (confirms DKIM status and verification status) and renders both.
- Surfaces the raw AWS error message inline if the call fails (bad/missing credentials, identity not found, wrong region) rather than a generic failure — that message is the fastest way to tell what's still missing.

`GetAccountSendingEnabled` was the originally-named call for this, but that's a SES **v1** API action; on the v2 API this repo uses (EMAIL_SPEC.md §1), the equivalent data comes back as the `SendingEnabled` field on `GetAccount`'s response, which is what the route actually calls.

## 6. What this does *not* cover

- Requesting SES **production access** (still sandboxed to verified recipients / 200 per day until you file that AWS Support case — EMAIL_SPEC.md §2).
- Any sending or receiving code — `EmailMessage`/`EmailThread`/`EmailEvent` and the actual send/webhook endpoints are separate, later work (EMAIL_SPEC.md §4–§5).
- SNS → app event delivery (SQS vs. webhook, EMAIL_SPEC.md §3) — the SNS topic exists and is wired after this setup, but nothing is subscribed to consume it yet.

## 7. Attachment storage (S3)

Email attachments (both sent and received) are stored in S3, never in Postgres — see `server/src/lib/attachmentStorage.ts` and CLAUDE.md's "Email attachments" section. There's no provisioning script for this (unlike §2 above) since a bucket is a one-line console/CLI action with no DNS propagation wait; do it manually:

1. Create a private S3 bucket (block all public access — attachments are only ever served via short-lived presigned URLs, never a public bucket policy).
2. Set `ATTACHMENTS_S3_BUCKET` (and `ATTACHMENTS_S3_REGION`, if different from `AWS_REGION`) in `server/.env`.
3. Attach the IAM policy at [`server/aws/s3-attachments-iam-policy.json`](./server/aws/s3-attachments-iam-policy.json) to the app's runtime role/credentials, substituting your real bucket name for `ATTACHMENTS_S3_BUCKET`. It grants only `s3:PutObject`/`s3:GetObject`, scoped to the `email-attachments/` prefix the app writes under — no `s3:ListBucket`, `s3:DeleteObject`, or bucket-level permissions, since the app never needs to enumerate or delete attachments.

Until `ATTACHMENTS_S3_BUCKET` is set, attachment upload/download is disabled: composing or replying with an attachment returns a 400, and inbound messages with attachments are stored without them (the message itself — subject, body, thread — is still synced normally). Everything else in the app works unaffected, same as SES/IMAP being optional.
